# 求职演示与讲解提纲

## 项目描述

“山野装备”是自营户外装备商城，包含用户端与运营后台。后端按账户、商品与库存、购物车、订单、支付和网关拆分，特色是固定套装与单品共享组件库存。交易链路采用本地事务、幂等资金账本、持久化操作恢复与 Outbox，覆盖支付、关单、退款和履约。

## 可以解释并演示的三个问题

**1. 为什么套装库存不能直接写一个数字？**

双人套装需要两把椅子，买一套再买一把椅子就是三把。先展开套装、汇总组件，再按确定顺序锁定组件和条件扣减。套装可售数量取组件库存除以需求数量后的最小值。订单保存组件快照，管理员日后改套装也不会影响已下订单的退款与库存恢复。

**2. 已扣款但交易服务没有收到成功结果，怎么办？**

订单先保存 PAYING；资金模块将余额变化和唯一操作编号一起提交。支付或交易服务重启后重复调用同一个编号，不会再次扣钱。支付状态与 Outbox 同事务落库，通知可重试；交易模块也会恢复处理中操作。它提供最终一致性，不把跨模块 HTTP 调用误称为同一个 ACID 事务。

**3. 退款与管理员发货同时发生，怎么办？**

两者都必须从 PAID 状态开始，在同一订单行锁内选择下一状态。先进入 REFUNDING 则禁止发货；先进入 SHIPPED 则禁止未发货退款。退款完成还需要资金退款与组件库存恢复，双方接口都按订单号幂等。

## 演示证据

独立集成脚本启动 9080–9085 和单独数据库，测试并发下单、缺货回滚、重复支付、低余额、退款/发货竞争、支付/取消竞争、服务中断恢复、库存不足和超时关单。浏览器脚本实际操作两个前端并保存截图。不要把这些功能等同于未经测试的生产吞吐量、高可用部署或真实支付接入。

## 已知规模和后续方向

当前目录和订单查询适合演示规模；目录筛选在前端，用户订单最多 100 条、管理员订单最多 200 条，后台统计按创建日期计算有效订单金额。后续可以基于真实数据量增加分页、索引、搜索服务、事件聚合、后台细分权限和操作审计，不需要为求职罗列未实现的技术。
